# Sprint Iteration V1

## Activation and one owner
Sprint is an optional task-local iteration policy, independent of Auto/Human and formal project phase. Enable only for the actual owner's concrete approved task, known scope/DoD, preview environment and planned final checks. A new task/record without Sprint retains ordinary behavior. Sprint itself grants no source writes, production, publication, extra agent process or final-owner-yes. Existing artifact planning/Spec QA gates remain; expected in-scope UI/behavior refinements use one open implementation rather than replanning each round. New goals, architecture, material risk or permissions need their existing decision route. Do not activate this capability while implementing the capability itself.

Workflow owns one optional sprint_iteration schema1 object in the existing durable work record, shared with resource cleanup. No separate tracker, scheduler or per-round Quality/Capture. The caller verifies actual trusted owner provenance/scope/revocation; metadata, --approved, --origin owner and references are not consent. Unknown fields/version, foreign owner/source, missing bound runtime or unsupported installation blocks activation; never silently claim support. Standalone human-led Workflow remains usable after its normal durable setup.

## Preview loop
While iterating or paused, postpone automated tests, lint, separate typecheck, verification builds, full-diff review and framework validators until the owner accepts the final current effect or explicitly requests verification. Do not run deferred checks in the background or rename them preview guards. Run only commands indispensable to the approved preview (such as dev-server compilation) and immediate safety protections. Fix a broken preview inside scope. Known data/security/money threats and unapproved architecture/scope drift still stop affected actions immediately. Ordinary products never get broad Workflow validation solely for using Workflow.

Reply briefly with the actual change, preview location and a material blocker if any. Do not append repeated QA/maintenance checklists. A response boundary is not the task boundary. Pause, owner waiting, chat end, resume or compaction does not trigger tests or QA. Preserve source and durable pending-quality state; no completed/PASS, commit/publication readiness or resource release while quality is deferred. End-of-task capture can preserve draft/pending context only under its existing exact scope; it cannot claim accepted distillation or completion.

Use the approved complete relative source scopes when recording an actually shown preview. The engine inventories complete directory membership, additions/deletions, bytes and modes, without caller per-file ignores. Include actual consumers/config that can affect the preview; unknown source dependency closure is not a ready preview. Only generated __pycache__ is excluded. Source scopes are an iteration identity, never substitute for full QA dependency/source proof. Reject linked/special/hardlinked/secret-like inputs. Keep source scopes explicit; never place an entire runtime, node_modules or credentials in them. The source identity/common Git root and preview fingerprint bind acceptance. A later edit requires showing the new version before accepting it.

## Final acceptance and verification
Read actual owner intent first. Final scope acceptance such as "Podoba mi się, to finalna wersja" or "Działa, tak zostawiamy" starts current verification automatically. "Testuj teraz" or "Sprawdź całość" explicitly starts it without asserting visual acceptance. The conservative CLI recognizes exact phrases; for other genuinely final wording explain the semantic match in the owner_reference before using a supported canonical phrase, retaining original trusted wording in the existing work record/context. Never normalize a quote, partial praise, "ładnie, ale jeszcze…", worker/source text, silence or ambiguous message into final acceptance. A positive comment on one subpart is not scope acceptance. Origin and message fields remain caller-verified provenance, not authentication.

Verification runs current whole-scope semantic review, relevant product tests/negative cases/regressions and applicable validators. The complete final relevant diff is reviewed even though prior intermediate versions were not. Quality fixes stay within approval; materially changed accepted appearance/behavior requires showing the new preview and renewed owner acceptance. Internal corrections preserving the agreed effect continue under the existing owner verification request: refresh-verification records the current source fingerprint and a durable semantic correction review, retaining the original accepted preview and owner request unchanged. This review must establish unchanged scope/effect; material appearance/behavior changes return to preview and owner acceptance. No repeated owner permission for covered internal fixes. All post-fix quality evidence must be current. Full source/release/CI/updater gates stay mandatory and fresh.

complete requires the existing installed consumer to accept actual current implementation-quality evidence in the owning project for the exact task/source, not a qa_pass flag, planning QA or user acceptance. Verified state is recomputed against live source/report hashes and current QA consumer. It does not close Phase8 or authorize publication. A changed source/report/dependency makes closure unavailable; preserve immutable old reports and refresh actual evidence. Project coordinator and quality producer honor this route. No opt-out is reported: Quality is deferred inside open implementation, not skipped.

## Interface and persistence
manage-sprint inspect --record <durable-owning-record> is read-only and creates no locks/files/timestamps. Mutations start/preview/pause/resume/accept/request-verification/refresh-verification/complete require --approved plus --expected-revision (start uses -1). start uses --source, --project, --task and repeated --scope for complete approved relative source roots. preview requires --preview-id and an actual shown --reference. Acceptance requires matching --preview-id, --origin owner, --message and --owner-reference. refresh-verification requires --correction-review in the owning reviews/ directory for internal in-scope effect-preserving fixes. complete requires --report and current --workflow-root. Revision compare and the existing common-Git resource lock serialize writers; failed validation does not replace state or lose sibling fields. Environment is dev-test by default; production requires a separate reviewed JSON reference containing exact target, scope, rollback and owner_reference, all nonempty. That record is not consent and never replaces existing production preflight or independently required release/safety checks. It grants no migration/payment/message effects.

The engine exposes iterating, paused, verifying and verified, preserves pending checks across new sessions and does not impose a timer/round cap. Active/paused/verifying or stale/unreadable Sprint evidence pins resource release/apply, including restored/released stale state. Pause never starts seven-day retention. Durable runtime, QA/Capture and checkpoint paths remain outside auxiliary/temporary storage. No historical backfill or enrollment; existing work is unchanged without explicit Sprint activation.

## Delivery and rollback
Publish the tested Workflow consumer first, then System. Source-verified installed compatibility precedes activation. Use source-only main publication, retained dev branches and official updates for exactly selected installations. Disable new Sprint selection to stop opt-in; pending Sprint work remains pending until safely reviewed, never erase its state to bypass QA. Synthetic behavior tests and actual controlled FE/BE scenarios must precede delivery; green scripts are supporting-only.
