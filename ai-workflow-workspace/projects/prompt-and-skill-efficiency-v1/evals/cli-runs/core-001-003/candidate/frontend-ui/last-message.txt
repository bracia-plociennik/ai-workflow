## Screen plan

**Proposed scope:** A “Profile” section with editable display name and preferred language, plus a read-only email address. Treat email, password, and other security-sensitive changes as separate flows requiring their own requirements and approval.

On wide screens, use a restrained settings navigation beside a single-column form. On narrow screens, stack the navigation, heading, fields, and actions; keep controls full width and prevent horizontal scrolling. Reuse the eventual project’s form, button, alert, and typography components.

| State | Screen behavior | User action |
| --- | --- | --- |
| Initial loading | Show stable form-shaped placeholders; disable Save. | Wait for account data. |
| Load failure | Show a clear error in the form area. | Retry loading. |
| Ready, unchanged | Show current values and a disabled Save button. | Edit a field. |
| Invalid input | Show a message beside each invalid field and an error summary on submit. Preserve values. | Correct and resubmit. |
| Saving | Keep entered values visible; disable duplicate submission and show progress. | Wait for confirmation. |
| Save success | Show a confirmation only after the server confirms; update the displayed values. | Continue editing if needed. |
| Save failure or offline | Preserve edits, explain that changes were not saved, and offer Retry. | Retry or keep editing. |
| Stale data conflict | Preserve edits and explain that account data changed elsewhere. | Reload current data, then review edits before saving. |

Use labels and instructions that remain visible, keyboard-accessible controls, visible focus, and status announcements for loading, errors, and success. Keep error messages tied to their fields. A retry must not silently discard unsaved input.

**Proposed implementation sequence, once a React project and scope are supplied:**

1. Inspect its routes, design system, data contract, and test setup.
2. Specify field rules and server error mapping; confirm whether stale-write detection is supported.
3. Build the responsive layout and explicit state transitions.
4. Verify keyboard flow, narrow and wide layouts, validation, failed load/save, retry, and confirmed success.
