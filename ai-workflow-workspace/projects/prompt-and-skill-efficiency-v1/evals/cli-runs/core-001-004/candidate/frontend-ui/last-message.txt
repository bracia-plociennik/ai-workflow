## Screen plan

**Scope:** Let a signed-in user view their login email, edit their display name and preferences, and save. Treat login email as read-only. Credential and email changes require a separate security scope.

**Layout:** Use a page heading and one clearly grouped form. At wide widths, keep the form at a comfortable reading width with a persistent, visible save area. At narrow widths, stack fields and make the save button full width. Long email addresses, error text, and increased text size must wrap without horizontal scrolling.

| State | Screen behavior |
| --- | --- |
| Initial load | Show labeled skeleton areas; keep editing and save unavailable. |
| Load failure | Explain that settings could not load and offer **Retry**. |
| Ready | Show current values and a disabled save button until something changes. |
| Invalid | Show errors beside fields, link them to inputs, and move focus to the first error on submit. Use server-provided rules as the final authority. |
| Saving | Keep entered values visible, prevent duplicate submits, and announce progress. |
| Saved | Show success only after the save is confirmed; update the displayed baseline. |
| Save failure or offline | Preserve the draft, explain the failure, and offer **Try again**. |
| Stale data or conflict | Preserve the draft, explain that settings changed elsewhere, and offer a reload path with an explicit warning before discarding edits. |
| Permission loss | Stop editing and explain why saving is unavailable. |

Use native labeled controls, visible focus, keyboard-operable recovery actions, and text announcements for errors and success. Do not rely on color alone.
