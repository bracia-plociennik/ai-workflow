## Synthetic dashboard plan

1. **Define the display contract.** For each balance, require wallet address, chain ID, asset identifier and symbol, atomic balance, decimals, and the block number and indexing time behind the value. Define how the read model marks unavailable or incomplete data.
2. **Design a compact balance view.** Show the wallet and chain, then each asset’s formatted balance and data freshness. Keep amounts from different assets separate. Show a portfolio value only if an approved valuation source and timestamp are later supplied.
3. **Map the states.** Cover loading, no assets, loaded, stale, partial, unavailable, offline, and retry. Label projected data clearly; never imply a pending refresh has confirmed a new balance. Include narrow-screen, keyboard, and screen-reader behavior in the later UI specification.
4. **Verify against local synthetic data.** Future UI tests should cover large integer amounts, differing decimals, zero balances, mismatched chain or address, stale blocks, partial responses, and failed retries. Use local mocked responses only.

**Acceptance conditions for a future implementation:** Every displayed amount maps to the correct wallet, chain, and asset; formatting preserves atomic-value precision; freshness and failures are visible; the UI has no signing, sending, approval, or transaction controls; and no contract or backend code changes are included.
