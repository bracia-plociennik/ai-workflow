## Screen plan

Use a centered content area with a page heading, short description, and sections separated by dividers. The provisional fields are **display name** (editable, required, 1–80 characters after trimming), **email** (read-only), and **notification preference** (toggle). Keep password, email-change, and other security flows outside this screen until their contracts are defined.

At narrow widths, stack labels, fields, messages, and actions in one column. At wider widths, allow labels and controls to align in two columns while keeping the form easy to scan. The save button must remain visible in normal document flow, with a comfortable touch target and no horizontal scrolling at 320 px.

| State | Expected behavior |
| --- | --- |
| Loading | Show a labeled loading region and stable placeholders; disable editing until values arrive. |
| Load failure | Show an error summary and **Retry**. Retry reloads the values. |
| Ready | Show current values; keep **Save** disabled until a value changes. |
| Invalid | Validate on blur and submit. Show field-specific text, connect it to the input, and move focus to the first invalid field after submit. Preserve all entries. |
| Saving | Disable duplicate submits and show progress without implying success. |
| Saved | Show a concise success status and clear the dirty state. |
| Save failure or offline | Preserve edits, explain what happened, and offer **Retry save**. Never silently discard entries. |
| Changed on server | If the eventual API reports a conflict, keep local edits and offer a way to reload server values before retrying. |

**Proposed verification:** Test the state transitions with a mocked data source; check display-name boundaries and duplicate submission; inspect at 320, 375, 768, and 1280 px; and manually check keyboard focus, error announcements, and retry behavior. These are future acceptance checks, not checks run in this read-only task.
