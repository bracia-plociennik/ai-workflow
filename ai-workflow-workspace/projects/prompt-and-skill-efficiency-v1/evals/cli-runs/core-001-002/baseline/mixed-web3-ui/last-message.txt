## Synthetic dashboard plan

1. **Data boundary:** The UI consumes an *existing* backend balance read model. It makes no direct chain-provider calls and has no signing, approval, transfer, or transaction controls.
2. **Balance view:** Show wallet address, chain, asset, balance, and the block or timestamp represented by the snapshot. Preserve integer base units until display formatting; apply the asset’s verified decimals and label rounding clearly. Omit fiat values unless an existing, attributable price source is part of the accepted data contract.
3. **Trust cues:** Label values as a backend projection of on-chain state. Show when data is stale, still indexing, or unavailable; never label a cached balance “live.”
4. **State coverage:** Design loading, zero balance, populated, partial data, stale, wrong network, access denied, and service failure states. Provide a read-only retry where the existing API supports it.
5. **Later verification:** Against an agreed mock response, check large balances and decimal precision, chain and asset identity, stale data, error recovery, mobile layout, keyboard use, and screen-reader labels. These checks are planned, not run.

**Risk:** The bounded UI concept is medium risk. A new provider integration, authentication change, or security claim would require separate risk review and approval.
